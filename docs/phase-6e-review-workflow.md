# Phase 6E — Review Workflow, Auditability, and Identity Boundary

## 1. Purpose

Phase 6E adds a durable, append-only human-review layer around the existing
advisory progression result.

The advisory answers what the software observed and classified. A review event
records what a reviewer subsequently did with that advisory. The review layer
does not alter the advisory, evidence, progression history, or workout state.

## 2. Review domain

**Implemented.** `ProgressionReviewEvent` stores:

- review event ID;
- patient ID;
- stable exercise ID;
- explicit side or null;
- deterministic advisory fingerprint;
- neutral disposition;
- reviewer reference;
- optional note;
- server-generated review timestamp;
- creation timestamp.

The model is separate from `Patient`, advisory evidence, workout results, and
assessment records.

## 3. Review lifecycle

**Implemented.**

1. No review event means the current advisory target is `UNREVIEWED`.
2. A review event means the target has been reviewed.
3. Multiple review events are allowed.
4. Events are append-only.
5. The latest event by server timestamp and event ID is the current
   disposition.
6. Earlier events remain unchanged and reconstructable.

`UNREVIEWED` is a derived absence-of-event state and is not persisted as a
redundant row.

## 4. Disposition semantics

The persisted neutral dispositions are:

```text
REVIEWED
ACKNOWLEDGED
DISMISSED
```

These do not mean clinically approved, safe, prescribed, progressing, or
regressing. The system deliberately does not persist clinical dispositions.

## 5. Append-only audit model

**Implemented.** Every POST creates a new `progression_review_events` row.
Changing `REVIEWED` to `ACKNOWLEDGED`, or `ACKNOWLEDGED` to `DISMISSED`, never
updates or deletes the previous event.

The database migration is:

```text
9e6c4d2b8a10_add_progression_review_events.py
```

Review timestamps are generated by the service, not trusted from the browser.
Tests may inject a timestamp through the service boundary only.

## 6. Advisory identity/reference

**Implemented.** Advisory decisions are computed rather than persisted.
Therefore each review targets a deterministic SHA-256 fingerprint derived from:

- patient ID;
- exercise ID;
- requested side;
- ordered canonical evidence records;
- relevant source, timestamp, status, repetition, score, and resistance
  fields.

The fingerprint:

- is stable for identical evidence;
- changes when relevant evidence changes;
- does not use Python `hash()`;
- excludes reviewer identity and note;
- does not duplicate the advisory evidence payload;
- does not create a second progression history.

Review history is only returned for the currently computed fingerprint, so
reviews for a changed evidence snapshot are not silently presented as current.

## 7. Reviewer identity abstraction

**Implemented.** `reviewer_reference` is a validated application boundary,
not authentication. It is a bounded opaque reference supplied by the current
trusted environment.

Phase 6E does not implement passwords, sessions, OAuth/OIDC, account
registration, authentication middleware, or authorization.

## 8. API

The read-only/current-history and append endpoints are:

```text
GET  /api/patients/<patient_id>/progression/advisory/reviews
POST /api/patients/<patient_id>/progression/advisory/reviews
```

Both require `exercise_id`; `side=left|right` is optional. POST accepts only:

```json
{
  "disposition": "REVIEWED",
  "reviewer_reference": "reviewer_demo_01",
  "note": "Optional untrusted note"
}
```

Unknown patients return `404`. Invalid exercise, side, disposition, reviewer
reference, note, or empty advisory target returns `400`.

The POST endpoint cannot modify classification, evidence, repetitions,
resistance, exercise, side, or workout state.

## 9. UI

The existing patient progression page now separates:

- **Software Classification**
- **Observed Evidence**
- **Limitations**
- **Human Review**
- **Review History**

The UI displays current derived review status, reviewer reference, server
timestamp, disposition, and escaped note text. After recording a review it
reloads review history without recalculating or mutating the advisory evidence.

No review can be created when the selected advisory has no evidence.

## 10. Security boundary

The intended future request flow is:

```text
request
  ↓
identity context
  ↓
authorization check
  ↓
review service
  ↓
persistence
```

Phase 6E currently has only the review service and a trusted opaque reviewer
reference. That reference is not proof of identity and does not provide
authorization.

## 11. Patient vs reviewer distinction

**Patient** is the clinical/assessment subject and existing profile entity.

**Reviewer/User** is the person operating Revaliv and a separate future
identity concept.

The Patient model was not retrofitted with account or authentication fields.

## 12. Explicit non-goals

Phase 6E does not:

- implement authentication or authorization;
- approve progression or regression;
- prescribe repetitions or resistance;
- modify workout plans or SessionEngine;
- alter scoring, perception, readiness, or live assessment;
- persist advisory decisions as clinical records;
- infer legacy side;
- convert resistance units;
- fabricate cancelled-session results;
- add clinical thresholds or claims.

## 13. Validation

**Implemented tests cover:**

- deterministic advisory identity;
- valid review creation;
- append-only history;
- latest disposition;
- reviewer and note validation;
- no-evidence guard;
- patient/exercise/side isolation;
- unknown patient and invalid request handling;
- legacy side semantics;
- escaped/untrusted note rendering;
- review UI states and absence of prescription language.

The configured database is restored and verified schema-only after tests.

## 14. Known limitations

- Reviewer references are not authenticated.
- Authorization is not implemented.
- Review events are not clinical records.
- Advisory decisions remain computed from current evidence rather than
  persisted snapshots.
- If historical source evidence is later deleted or changed, the fingerprint
  identifies the reviewed snapshot but does not itself preserve a full evidence
  copy.
- Browser visual automation remains limited by the existing Chromium/Snap
  environment.

## 15. Future authentication boundary

The identity alternatives and recommendation are documented separately in
`docs/phase-6e-identity-architecture.md`.

**PASS — Phase 6E establishes a separate, append-only, provenance-linked human
review layer without clinical approval or workout-runtime integration.**
